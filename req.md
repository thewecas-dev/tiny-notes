Expiring Notes Service — Requirements Overview The Expiring Notes Service is a small HTTP API that stores a piece of text and returns a short code; the note deletes itself after a set number of views or a set time, whichever comes first. Typical use: sharing a password, API key or one-off message that should not linger in chat history or email. Goals for v1: • Create a text note and get a short, shareable code back • Read a note by its code, consuming one view • Guarantee a note is never served after it runs out of views or time • Stay small enough to build in a weekend with one database file Scope v1 handles plain text only, stored in SQLite, with no user accounts. In scope • UTF-8 text notes up to 100 KB • View-count limit and time limit per note • Three endpoints: create, read, metadata • Atomic read-and-decrement so a note is never over-served • Input validation and clear JSON errors Out of scope (later versions) • File or image uploads • Encryption at rest • Compression • Object storage (S3, R2) • Password-protected notes • User accounts, authentication, rate limiting • Web UI Functional requirements A note is readable only while it has views left and has not passed its expiry time. FR-1 Create a note

The client sends content, and optionally max_views and expires_in (seconds).
Defaults: max_views = 1, expires_in = 86,400 (24 hours).
Allowed ranges: max_views 1–100; expires_in 60–604,800 (1 minute to 7 days).
content must be a non-empty string of at most 100 KB (UTF-8 bytes).
The server generates a unique random code of 8 URL-safe characters.
The server stores the note and returns the code, views_left and expires_at. FR-2 Read a note
The client requests a note by code.
If the note exists, has views_left > 0 and expires_at is in the future, the server returns its content and decrements views_left by 1.
When views_left reaches 0, the server deletes the note in the same operation.
Missing, expired and used-up notes all return the same 404, so callers cannot tell which case applies. FR-3 View metadata
The client requests metadata by code.
The server returns views_left, expires_at and created_at, never the content.
This request does not consume a view. FR-4 Expiry cleanup
Expired notes are never returned, whether or not they still exist in the database.
A background job deletes expired rows every 10 minutes so the database doesn't grow forever. API specification Three JSON endpoints; all requests and responses use Content-Type: application/json. Method Path Purpose Success POST /notes Create a note 201 Created GET /notes/{code} Read content, consumes one view 200 OK GET /notes/{code}/meta Read metadata, consumes nothing 200 OK POST /notes request: { "content": "db password: hunter2", "max_views": 1, "expires_in": 3600 } Response 201: { "code": "aB3xK9pQ", "views_left": 1, "expires_at": "2026-10-01T11:13:00Z" } GET /notes/{code} response 200: { "content": "db password: hunter2", "views_left": 0 } GET /notes/{code}/meta response 200: { "views_left": 1, "expires_at": "2026-10-01T11:13:00Z", "created_at": "2026-10-01T10:13:00Z" } All timestamps are ISO 8601 in UTC. Data model One SQLite table holds everything; content is a plain TEXT column. CREATE TABLE notes ( code TEXT PRIMARY KEY, content TEXT NOT NULL, views_left INTEGER NOT NULL CHECK (views_left >= 0), expires_at INTEGER NOT NULL, -- unix seconds, UTC created_at INTEGER NOT NULL -- unix seconds, UTC );
CREATE INDEX idx_notes_expires_at ON notes (expires_at); The index on expires_at keeps the cleanup job fast. Times are stored as integers to avoid time-zone parsing bugs; the API converts them to ISO 8601. Non-functional requirements The hardest requirement is NFR-2: a one-view note must reach exactly one reader, even under simultaneous requests. NFR-1 Size limit • Request bodies over 100 KB are rejected with 413 before the full body is read into memory. • Enforce the cap twice: in the framework's body parser and, if deployed behind nginx, with client_max_body_size. NFR-2 Atomic reads • Checking, decrementing and deleting must happen in one atomic step, never as separate read-then-write calls. • Recommended approach: a single conditional update inside a transaction: UPDATE notes SET views_left = views_left - 1 WHERE code = ? AND views_left > 0 AND expires_at > ? RETURNING content, views_left; • If no row comes back, respond 404. If views_left is now 0, delete the row in the same transaction. NFR-3 Security • Codes come from a cryptographically secure random generator, not a counter or timestamp. • Note content is never written to application logs. • All SQL uses parameterised queries. NFR-4 Performance • Each endpoint responds in under 50 ms locally for a 100 KB note. • No request does work proportional to the number of stored notes. NFR-5 Simplicity • One process, one SQLite file, no other services required to run it. Error handling and edge cases Every error returns JSON shaped { "error": "", "message": "" }. Situation Status error Body is not valid JSON 400 invalid_json content missing, empty or not a string 400 invalid_content max_views or expires_in out of range or not an integer 400 invalid_field Body larger than 100 KB 413 payload_too_large Code unknown, expired or out of views 404 not_found Unexpected server failure 500 internal_error Edge cases to handle: • Code collision: if a generated code already exists, generate a new one (retry up to 3 times, then 500). • Expired but not yet cleaned up: reads must check expires_at, not rely on the cleanup job. • Unknown fields in the body: ignore them. • Size counted in bytes, not characters: 100 KB of emoji is fewer characters than 100 KB of ASCII. • Whitespace-only content: treat as empty and reject. Acceptance criteria v1 is done when every test below passes in an automated test suite. [ ] Creating a note with only content returns 201, an 8-character code, views_left = 1 and an expiry 24 hours ahead. [ ] Reading a 1-view note returns the content once; the second read returns 404. [ ] A 3-view note can be read exactly 3 times. [ ] A note with expires_in = 60 returns 404 after 61 seconds, even before cleanup runs. [ ] /meta does not change views_left. [ ] A 100 KB body is accepted; a body of 100 KB + 1 byte returns 413. [ ] max_views = 0, 101 or "abc" each return 400. [ ] 20 simultaneous reads of a 1-view note produce exactly one 200 and nineteen 404s. [ ] Expired rows are gone from the database after the cleanup job runs. [ ] Note content never appears in the server log. Milestones Build in this order; each step ends with its tests passing.

Setup: project skeleton, SQLite connection, notes table.
Create: POST /notes with code generation and defaults (FR-1).
Read: GET /notes/{code} with expiry check and view decrement (FR-2).
Validation: size limit, field ranges and the error format (NFR-1, error table).
Concurrency: switch reads to the atomic update and add the 20-request test (NFR-2).
Metadata: GET /notes/{code}/meta (FR-3).
Cleanup: the background job for expired rows (FR-4). Future enhancements (after v1): encryption at rest, password-protected notes, rate limiting per IP, file uploads via object storage, and a minimal web page for non-developers.
